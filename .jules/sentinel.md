## 2024-05-24 - [Wildcard Injection in PowerShell Cmdlets]
**Vulnerability:** Found wildcard injection vulnerabilities in `find duplicated based on folder.ps1` and `find-duplicated-video.ps1`. When using the `-Path` parameter in cmdlets like `Get-ChildItem`, `Test-Path`, `Move-Item`, and `Get-FileHash`, PowerShell interprets square brackets `[]` and other wildcard characters in filenames. This can cause cmdlets to either fail or act on unintended files if a user-controlled file path contains these characters.
**Learning:** In PowerShell scripts dealing with arbitrary file paths or user input, always use `-LiteralPath` instead of `-Path` to prevent paths from being evaluated as wildcard patterns, avoiding unintended consequences or execution failures.
**Prevention:** Default to using `-LiteralPath` for all path-based cmdlets unless wildcard evaluation is explicitly intended and strictly controlled.
## 2024-03-24 - Directory Scoping Bypass via Path Confusion
**Vulnerability:** Path confusion vulnerability in `find-duplicated-video.ps1`.
**Learning:** Using `String.StartsWith()` for filtering paths without appending a directory separator can unintentionally include similarly named sibling directories. E.g., filtering for `D:\MyFolder` will incorrectly match `D:\MyFolder_Secret\video.mp4`. Furthermore, default `StartsWith()` in .NET is case-sensitive, making it unreliable for Windows file paths.
**Prevention:** Always normalize directory paths by appending a trailing slash (e.g., `TrimEnd('\') + '\'`) and use `[System.StringComparison]::OrdinalIgnoreCase` when comparing paths using `.StartsWith()`.
## 2023-10-29 - Missing Error Handling Exposing Stack Traces
**Vulnerability:** Found a missing error handler in `find-duplicated.py` for the `os.remove()` call. If a file was locked or missing permissions, it would crash the program and expose a stack trace.
**Learning:** File system operations can fail for many reasons outside the program's control. Unhandled exceptions in these operations can leak information about the system through stack traces.
**Prevention:** Always wrap file operations in `try-except OSError` blocks to fail securely, handle the error gracefully, and log a controlled message instead of a stack trace.
## 2024-05-24 - TOCTOU Vulnerability in File Move Operations
**Vulnerability:** Found a Time-of-Check to Time-of-Use (TOCTOU) vulnerability in `find duplicated based on folder.ps1` and `find-duplicated-video.ps1`. When moving duplicate files to a quarantine folder, the scripts used `if (Test-Path)` to check for existence and then `Move-Item -Force` to move the file. This creates a race condition where if a file with the newly generated name is created in the destination between the check and the move, the `-Force` flag will cause `Move-Item` to silently overwrite it, leading to potential data loss.
**Learning:** Checking for file existence before performing an operation is not atomic. In concurrent or multi-process environments, the state can change between the check and the use. Using `-Force` on operations like `Move-Item` can mask this race condition and lead to destructive silent overwrites.
**Prevention:** Use a `while` loop that increments a counter to ensure a unique destination name, and critically, remove the `-Force` flag from `Move-Item` (or use `-ErrorAction Stop`) so that if a collision does happen despite the check, the operation fails safely rather than overwriting data.
## 2024-10-30 - [Information Leakage via Unhandled Exceptions & Predictable File Overwrite]
**Vulnerability:** Found two vulnerabilities in `find duplicated based on folder.ps1`:
1. `Get-ChildItem -Recurse` lacked error handling, causing it to leak sensitive directory structures and permission states to the console/logs when encountering inaccessible (protected/system) directories.
2. The script exported results to a hardcoded, predictable path (`Desktop\DuplicateFilesReport.csv`), creating a risk of symlink attacks or predictable file overwrite.
**Learning:** File system operations scanning wide directory trees must handle permission denied errors securely to prevent information leakage. Additionally, static output paths for reports or logs open systems up to symlink vulnerabilities or data loss.
**Prevention:** Always use `-ErrorAction SilentlyContinue` (or try-catch blocks) when scanning file systems to suppress and securely handle unauthorized access exceptions. Use dynamic, timestamped filenames (e.g., `_$(Get-Date -Format 'yyyyMMdd_HHmmss')`) for generated reports to prevent predictable overwrite vulnerabilities.
## 2024-10-31 - [Information Leakage via Unhandled Exceptions in Basic Operations]
**Vulnerability:** Found vulnerabilities in PowerShell scripts (`find duplicated based on folder.ps1` and `find-duplicated-video.ps1`) where simple file system operations like `New-Item` and `Export-Csv` lacked proper error handling. If operations failed (e.g. invalid path, insufficient permissions, read-only media), the scripts would crash and expose full stack traces.
**Learning:** Even simple, seemingly safe operations like creating a folder (`New-Item`) or saving a report (`Export-Csv`) can fail due to environment constraints. Unhandled exceptions leak structural and permission details via stack traces, increasing the attack surface.
**Prevention:** Always wrap any file system operation in a `try...catch` block with `-ErrorAction Stop`. In the `catch` block, use `Write-Error` or `Write-Warning` to log the user-friendly exception message (`$_.Exception.Message`) to maintain debuggability without exposing stack traces.
## 2024-11-01 - [Information Leakage via Unhandled Exceptions in Get-FileHash]
**Vulnerability:** Found vulnerabilities in PowerShell scripts (`find duplicated based on folder.ps1` and `find-duplicated-video.ps1`) where `Get-FileHash` cmdlets inside `try-catch` blocks were missing the `-ErrorAction Stop` parameter. If a file was locked or inaccessible, the cmdlet would generate a non-terminating error that bypassed the `catch` block, leaking error details directly to the console.
**Learning:** In PowerShell, only terminating errors trigger a `catch` block. Non-terminating errors (like those from file permission issues in cmdlets) bypass exception handling entirely unless `-ErrorAction Stop` is explicitly provided, which can lead to information leakage and unpredictable script state.
**Prevention:** Always append `-ErrorAction Stop` to file operation cmdlets like `Get-FileHash` when used inside `try/catch` blocks to ensure all exceptions are caught and handled securely.
## 2024-11-09 - [Anti-Pattern: Security Theater via Obfuscated System Exceptions]
**Vulnerability:** Obfuscating standard system exceptions (like `OSError` or 'File not found' / 'Access Denied') in local CLI utility scripts is considered "security theater" and degrades debuggability. By omitting the actual exception message, developers must guess why an operation failed (e.g., file lock, missing permissions, bad path), which complicates administration.
**Learning:** While stack traces should be suppressed to avoid leaking internal script state and structure, the actual standard exception message from the operating system should remain visible. Hiding it provides no meaningful security benefit for local utilities while creating significant operational friction.
**Prevention:** In CLI utilities, catch exceptions to prevent stack trace leaks, but explicitly log or output the exception message (e.g., `$_.Exception.Message` in PowerShell or `str(e)` in Python) to inform the user of the failure reason.
## 2024-11-10 - [Information Leakage via Unhandled Exceptions in Future Results]
**Vulnerability:** Found missing error handling in `find-duplicated.py` for asynchronous worker results (`future.result()`) and top-level `main()` execution. If an unexpected error occurred inside a worker process (e.g. failing to open a file with a non-standard error, corrupted images out of PIL's expectation, or memory issues), the unhandled exception propagated out, crashing the main thread and leaking the full stack trace to the terminal.
**Learning:** Asynchronous workers (Futures) abstract away execution but still bubble up exceptions when their `.result()` is consumed. Unhandled exceptions here, or at the top level of a script, will expose internal state and structural details via stack traces.
**Prevention:** Always wrap `future.result()` in a `try-except` block when consuming tasks from a `ProcessPoolExecutor` or `ThreadPoolExecutor`. Furthermore, ensure the top-level execution block (e.g., `main()`) catches `Exception` and `KeyboardInterrupt` to fail securely and handle termination signals without leaking stack traces.
## 2024-11-11 - [Denial of Service via Massive Files]
**Vulnerability:** Found a lack of file size limits before loading operations in `find-duplicated.py`. Without bounds, an attacker (or accidental misconfiguration) could supply massively oversized files (e.g., multi-gigabyte crafted raw/jpg files) causing memory exhaustion or CPU starvation (DoS) when attempted to be read by `PIL` or `rawpy`.
**Learning:** Checking file constraints immediately before processing, rather than relying solely on image pixel bounds (`Image.MAX_IMAGE_PIXELS`), prevents memory exhaustion during the initial loading phase. This must be implemented at the point of processing, rather than purely in a filename-matching function, to ensure valid pairs are still evaluated while protecting the image libraries.
**Prevention:** Always implement max file size boundaries (e.g., via `os.path.getsize()`) before calling memory-intensive operations like `Image.open()` or `rawpy.imread()` to avoid resource exhaustion attacks.
